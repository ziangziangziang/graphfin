# Phase 0 baseline results

## What belongs here

| File | Committed? | Purpose |
|---|---|---|
| `baseline.json` | yes | The authoritative Phase 0 baseline, recorded on the pinned arm64 image |
| `BASELINE.md` | yes | Human-readable report generated by `../report.py` |
| `baseline-ci.json`, `BASELINE-CI.md` | optional | amd64 CI numbers; **not** comparable to the arm64 baseline |
| `smoke.json`, `SMOKE.md` | no | Throwaway smoke runs from CI |

Regenerate the report after any re-run:

```bash
python3 ../report.py baseline.json -o BASELINE.md
```

## Comparability rules

A number from this directory is only meaningful next to the environment block
embedded in the JSON. Before comparing two results, check that these match:

1. `env.container.image_id` — the pinned compile image (see
   `ci/phase0/images.lock`). A different image means a different toolchain.
2. `env.host.arch` — **do not compare arm64 and amd64 numbers.**
3. `env.cpu.count`, `env.memory.cgroup_limit_bytes`, `env.limits.*` — the
   benchmark is resource-sensitive, especially thread and fd counts.
4. `env.storage.data_dir_fstype` — the scratch volume filesystem affects
   storage, snapshot and restore timings.
5. `config.max_size_gb`, `config.phases`, `config.repeated_queries`,
   `config.throughput_seconds` — the run configuration itself.

If any of these differ, the runs are separate experiments, not a comparison.

## Reading the result

The key scaling number is `runs.<N>.restart.seconds`: the server is stopped and
started again with N graphs already on disk, which isolates
`GraphManager::ReloadFromDisk` (`src/db/graph_manager.cpp:257-284`) — the
sequential, eager open of every graph at startup.

`runs.<N>.create.buckets` groups graph-create latency by how many graphs already
existed, which exposes the O(N) copy-on-write cost of `Galaxy::CreateGraph`
(`src/db/galaxy.cpp:192-193`) from a single run.

`runs.<N>` also records per-phase `error` fields and, where relevant,
`peak_observed` resource values at the moment of failure. A phase that failed is
a result: it identifies where the current implementation stops scaling.

Interpretation belongs in `docs/architecture/07-scalability-risks.md`; link any
new finding to a risk entry there rather than only describing it here.
